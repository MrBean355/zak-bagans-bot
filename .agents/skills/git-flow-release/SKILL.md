# Git Flow Release Skill

This skill guides you through cutting, finalizing, and publishing a software release for
this repository using **Git Flow**, generating standard GitHub release notes, and uploading
the compiled artifact (`zakbot.jar`).

---

## Repository Conventions & Architecture

* **Production Branch**: `main`
* **Development Branch**: `develop`
* **Release Branch Prefix**: `release/` (e.g., `release/3.2.0`)
* **Tag Format**: Annotated tag `v<version>` (e.g., `v3.2.0`) with tag message `<version>`
* **Release Title on GitHub**: `<version>` (e.g., `3.2.0`)
* **Compiled Artifact**: `build/libs/zakbot.jar` (generated by `./gradlew bootJar` on `main`)
* **Build File**: `build.gradle.kts`
* **Commit Message Format**: Follow project and Git commit conventions (imperative mood, 50-char subject, blank line, 72-char wrapped body). See [commit-messages.md](../../rules/commit-messages.md).

---

## Prerequisites & Pre-Flight Checks

Before starting any release, execute the following pre-flight checks:

1. **Verify Clean Working Tree**:
   Ensure no uncommitted changes or untracked files remain:
   ```bash
   git status --porcelain
   ```
   If dirty, stash or commit changes before proceeding.

2. **Verify Branch & Sync**:
   Start on the `develop` branch and ensure local branches are up to date with remote:
   ```bash
   git checkout develop
   git pull origin develop
   git fetch origin main:main
   ```

3. **Verify GitHub CLI Authentication**:
   Ensure `gh` is authenticated with appropriate repository write permissions:
   ```bash
   gh auth status
   ```

4. **Determine Release and Next Development Versions**:
   * Inspect current version in `build.gradle.kts`.
   * Agree on `<version>` (e.g. `3.2.0`) and next development version `<next_version>` (e.g. `3.3.0`).

## Step-by-Step Release Workflow

### Step 1: Pre-Release Verification & Test Suite

Verify that the current codebase on `develop` passes all tests cleanly before branching:

```bash
./gradlew clean test
```

Do not proceed if any tests fail.

---

### Step 2: Start Release Branch & Set Version

1. Create the release branch off `develop`:

#### Option A: Using `git-flow` CLI
```bash
git flow release start <version>
```

#### Option B: Standard Git (Reliable in non-interactive / agent environments)
```bash
git checkout -b release/<version> develop
```

2. Confirm `version = "<version>"` in `build.gradle.kts`.
   If updated, commit the change:
   ```bash
   git commit -am "Prepare for release <version>"
   ```

---

### Step 3: Finish the Release Branch

Merge the release into `main`, create the release tag, and merge back into `develop`.

#### Option A: Using `git-flow` CLI
```bash
GIT_MERGE_AUTOEDIT=no git flow release finish -m "<version>" <version>
```

#### Option B: Standard Git Commands (Zero interactive prompts)
```bash
# 1. Merge release branch into main
git checkout main
git merge --no-ff release/<version> -m "Merge branch 'release/<version>'"

# 2. Create annotated release tag
git tag -a "v<version>" -m "<version>"

# 3. Merge release tag into develop
git checkout develop
git merge --no-ff "v<version>" -m "Merge tag 'v<version>' into develop"$'\n\n'"<version>"

# 4. Remove temporary release branch
git branch -d release/<version>
```

---

### Step 4: Bump Version on `develop` for Next Development Cycle

1. On `develop`, update `version = "<next_version>"` in `build.gradle.kts`.
2. Commit the bump using project commit conventions:
   ```bash
   git add build.gradle.kts
   git commit -m "Prepare for development of <next_version>"
   ```

---

### Step 5: Build Production Artifact off `main`

Switch to the `main` branch so that the Spring Boot build metadata and jar are compiled strictly from the tagged release commit:

```bash
# Check out main
git checkout main

# Build production Spring Boot jar off main
./gradlew bootJar

# Verify artifact exists and has non-zero size
ls -lh build/libs/zakbot.jar

# Return to develop
git checkout develop
```

---

### Step 6: Push Branches and Tags to Remote

Push both updated branches and tags to GitHub:

```bash
git push origin main develop --tags
```

---

### Step 7: Draft Release Notes

1. Identify the previous tag:
   ```bash
   PREV_TAG=$(git describe --tags --abbrev=0 "v<version>^")
   ```

2. Inspect commits since the previous release:
   ```bash
   git log "${PREV_TAG}..v<version>" --oneline
   ```
   Or run the [changelog helper script](scripts/generate-changelog.sh):
   ```bash
   .agents/skills/git-flow-release/scripts/generate-changelog.sh "${PREV_TAG}" "v<version>"
   ```

3. Compose release notes emphasizing **behaviour changes** rather than mechanical code details:
   * **Keep it Concise**: 1–2 crisp sentences per bullet point (`• `). No waffle, no commit hashes, and no low-level method or class names.
   * **Focus on Behaviour**: Highlight observable changes in bot replies, keywords, comment commands, rate limits, alerts, or fixed runtime issues.
   * **Filter Internal Noise**: Omit minor chores, tests, and invisible internal refactoring unless there is a notable operational or architectural impact (which goes under `## 🔧 Technical`).

4. Format using established project sections:
   * `## ✨ New Features` (new commands, phrases, praise replies)
   * `## ⚙️ Enhancements` (improvements to matching logic, command syntax, notifications)
   * `## 🐛 Bug Fixes` (crashes prevented, skipped comments fixed, connection issues handled)
   * `## 🔧 Technical` (sparingly used for major dependency/framework upgrades or architecture overhauls)
   * `Full Changelog: https://github.com/MrBean355/zak-bagans-bot/compare/<prev_tag>...v<version>`

See the template at [release-notes-template.md](resources/release-notes-template.md) for a reference layout.

Save notes to a temporary file (e.g., `release_notes.md` or in the agent's scratch directory).

---

### Step 8: Publish GitHub Release & Upload Artifact

Publish the release with the compiled jar attached:

```bash
gh release create "v<version>" build/libs/zakbot.jar \
  --title "<version>" \
  --notes-file release_notes.md
```

Verify that the release is live and the asset is attached:

```bash
gh release view "v<version>"
```

Clean up temporary notes file if created locally.

---

## Rollback & Troubleshooting

* **Build/Test Failure on Release Branch**:
  If tests or compilation fail after branching, delete the release branch and return to `develop`:
  ```bash
  git checkout develop
  git branch -D release/<version>
  ```
* **Git Flow Abort**:
  If a merge conflict occurs during finish, resolve conflicts or abort via `git merge --abort`.
* **GitHub Release Asset Update**:
  If an asset needs re-uploading without recreating the release:
  ```bash
  gh release upload "v<version>" build/libs/zakbot.jar --clobber
  ```
